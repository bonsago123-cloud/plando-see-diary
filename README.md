## 인증 구현 설명서

### ① 무엇으로 붙였나

이메일·비밀번호와 데이터베이스 세션을 직접 구현했다. 인증 프레임워크는 사용하지 않았다. 비밀번호 파생은 Node.js 표준 `node:crypto`의 scrypt를 사용한다. 잠금 파일 기준 Next.js 16.4.3, React 19.3.1, `@neondatabase/serverless` 1.2.0이다.

### ② 왜 그걸 골랐나

기존 Neon 데이터와 Next.js API를 유지하면서, 로그아웃 때 서버 세션을 폐기하고 계정별 자료 소유권을 검사하도록 했다. Supabase Auth 같은 외부 인증 서비스도 검토했지만 기존 Neon 구조를 유지하고 새 서비스 설정을 늘리지 않기 위해 선택하지 않았다. 무효화하기 어려운 자체 JWT 방식 대신 서버에서 폐기할 수 있는 세션을 사용했다. scrypt는 Node.js의 검증된 구현이고 계정별 무작위 salt를 사용한다.

### ③ 어디를 어떻게 고쳤나

| 흐름 | 구현 위치 |
|---|---|
| 첫 화면·가입·로그인 | `app/page.tsx`, `app/login/login-form.tsx`, `app/api/auth/[action]/route.ts` |
| 비밀번호 해싱 | `lib/password.ts` — scrypt, 계정별 16바이트 salt |
| 세션 발급·검증·폐기 | `lib/auth.ts` — 12시간 만료, HttpOnly 쿠키, DB 세션 폐기 |
| 기록 화면 로그인 확인 | `app/diary/page.tsx` |
| 계정 소유권이 적용된 조회·수정·삭제·내보내기 | `app/api/data/route.ts`, `lib/rules.ts` |
| 계정 자료 이전 | `scripts/assign-legacy-owner.mjs`, `lib/legacy-transfer.mjs` |
| 데이터베이스 변경 | `db/migrations/20261026_auth.sql` 및 이후 migration 파일 |

같은 이메일의 중복 가입은 막고, 없는 이메일과 틀린 비밀번호는 같은 401 문구를 반환한다. 세션은 URL에 넣지 않고 DB에는 원문 대신 SHA-256 해시를 저장한다. 로그아웃과 비밀번호 변경은 서버 세션도 폐기한다. `.env.local`은 Git에서 제외된다.

### ④ 열리지 않는지 확인한 기록

`docs/auth-test-results.md`에는 실제 Next.js 요청 처리 함수와 PGlite PostgreSQL을 사용한 로컬 통합 검사의 마스킹된 요청·응답이 있다. 익명 자료 요청 401, 잘못된 비밀번호와 없는 계정의 동일한 오류, 서로 다른 salt를 쓴 임시 계정의 해시, 양방향 타인 자료 접근 차단과 거절 전후 데이터 비교가 기록되어 있다. 이는 실제 Vercel·Neon을 통한 브라우저 네트워크 캡처와 구분한다.

실제 서비스에서 이번에 확인한 것은 로그인된 계정의 5일 집계와 보관 처리 후 화면이다. 시크릿 창에서 로그인 전 화면, 운영 서버의 세션 만료·로그아웃 응답, 두 실계정 간 자료 접근은 직접 캡처하지 않았다. 비밀번호·쿠키·토큰 원문을 제출하지 않는다.

### ⑤ AI와 나

- AI가 한 일: 인증·계정별 소유권 코드를 구현하고, 테스트 및 설명 문서 초안을 작성했으며, 사이트 기록의 계산과 README 정리를 도왔다.
- 내가 직접 판단한 일: 수면 질문과 관찰 기준, 1~2일차 취침 규칙과 8시간 상한 규칙, 10월 29일 기록을 추가 관찰로 분리하는 일, 결과 해석과 결론을 정했다.
- AI 제안 중 따르지 않은 일: 과도하게 긴 기록 양식 대신 필요한 질문만 남기도록 요청했다. 수면 기록과 결론은 실제로 관찰·판단한 내용으로 유지했다.

### ⑥ 아직 못 막은 것

이메일 소유 확인과 비밀번호 재설정, 두 번째 인증 수단은 없다. 분산된 대량 로그인 시도를 충분히 막는 장치도 부족하다. DB 관리자 권한이 탈취되는 경우까지 막거나 이미 공개됐던 과거 자료를 회수하지는 못한다. 자동 통합 검사는 로컬 임시 데이터베이스 기준이며 운영 배포 환경 검증을 대신하지 않는다.

## 5일 사용 기록

### 고정한 질문과 계산 기준

- 질문: **잠자리에 드는 시각과 잠들기까지 걸리는 시간은 어떤 관련이 있을까?**
- 지표·단위: 잠들기까지 걸린 시간 / 분.
- 계산식: 잠든 시각 − 누운 시각. 날짜가 바뀌면 날짜를 포함해 계산한다.
- 잠든 시각은 다음 날 기억을 바탕으로 추정했다. 실제 수면량은 잠든 시각부터 기상 시각까지로 계산했다.
- 누운 시각 또는 잠든 시각이 불명확하면 합계·평균에서 제외한다. 같은 날짜의 중복 기록은 한 건만 계산한다. 입력 오류만 수정하고 실제로 오래 걸린 값은 유지한다. 평균은 합계 ÷ 유효 기록 수이며 소수점 셋째 자리에서 반올림한다. 주 시작 요일은 월요일이다.

|---|---|---|---:|---|---|---|

10월 29일 밤 기록은 새 규칙을 저장한 시각보다 먼저 실제로 잠든 기록이어서 5일 비교에서 제외했다. 이 추가 관찰은 아래에 따로 표시했다. 따라서 비교 대상 5일은 서로 다른 실제 날짜이며, 연속된 날짜일 필요는 없다.

### 계획 규칙 변경

- 변경 전: 1~2일차에는 밤 9시 30분 이전에 잠자리에 눕는다.
- 변경 후: 잠자는 시간을 평소와 동일하게 하되 수면량을 8시간 넘기지 않는다.
- 사이트에 새 규칙을 처음 저장한 시각: **2026-10-30 11:58:23 KST**.
- 마지막 문구 수정 시각: 2026-10-30 11:59:37 KST. 사이트 이력의 사유는 맞춤법 수정이다.
- 변경 이유: 1·2일차에 비슷한 시각에 누웠지만 잠들기까지 15분과 141분으로 달랐다. 수면량도 관계가 있을지 살펴보기 위해 규칙을 바꿨다.
- 이 시각은 새 규칙을 사이트에 저장한 시각이다. 실제로 규칙 변경을 결정한 시각이라고 주장하지 않는다. 변경은 2일차 결과 뒤, 3일차 실제 기록 전에 이뤄졌다.

### 10월 29일 추가 관찰

| 실제 날짜 | 누운 시각 → 잠든 시각(추정) | 잠들기까지 | 보고한 수면량 | 최초 기록(KST) | 상태 |
|---|---|---:|---|---|---|
| 2026-10-29 | 22:43 → 23:01 | 18분 | 약 7시간 30분 | 2026-10-30 10:13:13 | 사이트에서 보관 처리, 합계 제외 |

사용자가 추가 관찰로 남기길 원한 이 기록은 보관 처리했다. 일반 기록 목록과 대시보드 집계에서는 제외되고, 전체 내보내기에는 보존된다. 따라서 과제 비교에 사용하는 활성 기록은 서로 다른 날짜 5일이며, 10월 29일 기록은 별도 추가 관찰로 구분한다.

### 손계산과 사이트 집계

- 변경 전 1~2일차: 15 + 141 = **156분**, 평균 156 ÷ 2 = **78분**.
- 변경 후 3~5일차: 15 + 10 + 11 = **36분**, 평균 36 ÷ 3 = **12분**.
- 5일 합계: 156 + 36 = **192분**.
- 5일 평균: 192 ÷ 5 = **38.4분**.
- 사이트 대시보드: **5일 · 192분 · 평균 38.4분**. 5일 손계산과 일치한다.

### 내 결론과 한계

**내 결론:** 잠을 지나치게 많이 자지 않는 것이 잠드는 데 걸리는 시간을 줄이는 데 큰 영향을 준다고 생각한다. 규칙 변경 전 평균은 78분, 변경 후 평균은 12분이었다.

이는 5일간의 관찰에 대한 내 해석이다. 첫 두 날의 실제 수면량은 기록하지 않았고, 규칙 변경 후에는 잠자리에 든 시각도 달라졌다. 따라서 수면량 하나가 차이를 만들었다고 이 기록만으로 증명할 수는 없다. 특히 잠들기까지 짧은 시간과 충분한 수면은 서로 다른 지표다.

1. 어디로 가나요: 새 시크릿 창에서 위 결과물 주소를 엽니다.
2. 세 단계 안에 무엇을 하나요: 로그인 화면 확인 → 시험 계정으로 로그인 → `/diary`를 열고 로그아웃한 뒤 같은 주소를 다시 엽니다.
3. 무엇이 보이면 통과인가요: 로그인 전에는 로그인 화면, 로그인 뒤에는 본인 자료, 로그아웃 뒤에는 다시 로그인 화면이 보입니다.
